# Eventos no lucid-case

> **TLDR**: todo Command passa a gerar um Case event (sucesso e falha, e por step quando assinado), pode emitir Custom events com `emit`, e um novo kind `Lucid::Case::Subscriber` reage a eles via `subscribe`; os eventos vão para um outbox na mesma transação dos dados e um relay os entrega via ActiveJob (ou um transport do app), com deduplicação e ordem opt-in, e queries ganham `stale_on` para invalidar cache quando um evento acontece.

Vocabulário: `docs/CONTEXT.md` (Event, Case event, Custom event, Subscriber, Delivery, Outbox, Relay, Transport, Instrumentation). Decisão: `docs/adr/0001-transactional-outbox-for-events.md`. Consumidor de referência: luneta (`docs/specs/20261118150000_activity_events.md` e `config/initializers/subscribers.rb` daquele repo), migrado em spec futura.

# what

Como dev de um app Rails que usa lucid-case, quero que meus commands publiquem eventos com garantia transacional e que outros cases reajam a eles sem que o publicador os conheça, para parar de publicar `ActiveSupport::Notifications` à mão (às vezes antes do commit) e de acoplar efeitos colaterais dentro dos commands.

## out of scope

- Migrar o luneta (`ApplicationUseCase`, `subscribers.rb`, `pedagogical.*`): spec futura no repo do luneta.
- Adapters prontos de SQS, RabbitMQ ou qualquer broker: a gem entrega a interface de Transport, o adapter `:active_job` e um guia de como escrever um adapter.
- Trilha de auditoria (ator, IP, LGPD): o outbox não é log de auditoria; retenção curta e regras de PII ficam no app.
- Linhas de log e instrumentação (`ActiveSupport::Notifications`) de gravação/entrega de eventos.
- Painel/UI para eventos pendentes ou com falha.
- Deduplicação ou ordem para o store `:inline`.

## acceptance criteria

### Case event

    Cenário: command com sucesso gera Case event
      Dado config.events.recording = :enabled e store :outbox
      E `Enrollment::Approve < Lucid::Case::Command` que devolve success(enrollment: enrollment)
      Quando chamo Enrollment::Approve.call(enrollment: enrollment) e a transação commita
      Então existe 1 linha em lucid_case_events com kind "case", name "enrollment.approve", source "Enrollment::Approve", result_type "ok"
      E o payload guarda input e content serializados por ActiveJob::Arguments (o record como GlobalID)

    Cenário: input filtrado por filter_parameters
      Dado filter_parameters [:password]
      Quando Users::Create.call(params: { email: "a@x.com", password: "123456" }) tem sucesso
      Então event.input[:params][:password] é "[FILTERED]" e event.input[:params][:email] é "a@x.com"

    Cenário: falha gera Case event mesmo com rollback
      Dado um command transacional que grava um User e devolve failure(:card_declined)
      Quando é chamado
      Então o User não existe no banco
      E existe 1 Case event com result_type "card_declined", gravado depois do rollback do case

    Cenário alternativo: exceção não gera evento
      Quando um command levanta RuntimeError sem catch
      Então nenhuma linha é gravada em lucid_case_events e a exceção sobe
      E quando um catch converte a exceção em failure(:timeout), é gravado um Case event com result_type "timeout"

    Cenário alternativo: rollback da transação externa leva o evento junto
      Dado um command chamado dentro de ActiveRecord::Base.transaction que faz raise ActiveRecord::Rollback depois
      Então nenhuma linha fica em lucid_case_events e nenhum assinante é chamado

    Cenário alternativo: payload não serializável falha alto
      Dado um command que devolve success(callback: -> {})
      Quando é chamado
      Então levanta Lucid::Case::Error::UnserializableEvent e nada do case persiste
      E com event_payload { |result| { user_id: result[:user].id } } o evento grava só content { user_id: } e input {}

    Cenário alternativo: eventos desligados
      Dado config.events.recording = :disabled (default)
      Quando qualquer command é chamado
      Então nada é gravado nem entregue, e nenhuma tabela de eventos é consultada
      E um command com `events :enabled` grava mesmo assim, e com `events :disabled` não grava com o global ligado

### Custom event

    Cenário: emit dentro do command
      Dado Payment::Charge que chama emit(:credit_limit_reached, customer_id: 9) e devolve success
      Quando a transação commita
      Então existem 2 eventos: o Case event "payment.charge" e o Custom event kind "custom", name "credit_limit_reached", content { customer_id: 9 }

    Cenário alternativo: emit some com o rollback
      Dado um command transacional que emite e depois devolve failure
      Então o Custom event não existe; só o Case event de falha

    Cenário alternativo: emit fora de command
      Quando uma Query ou um Subscriber chama emit
      Então levanta Lucid::Case::Error::EmitOutsideCommand

### Steps ("o evento segue os dados")

    Cenário: step assinado em case transacional que falha depois
      Dado Order::Place com steps reserve_stock e charge_card, e um Subscriber de (Order::Place, step: :reserve_stock)
      Quando reserve_stock faz continue e charge_card devolve failure
      Então não existe Step event de reserve_stock e o assinante não é chamado

    Cenário: step assinado em case com transaction :disabled
      Dado Provisioning::Run com transaction :disabled e um Subscriber de step: :start
      Quando start faz continue e o step seguinte levanta exceção
      Então o Step event de start existe (kind "step", step "start") e é entregue

    Cenário alternativo: step sem assinante não grava
      Dado nenhum Subscriber de Order::Place com step:
      Quando o case roda
      Então nenhuma linha kind "step" é gravada

### Subscriber

    Cenário: Subscriber reage ao Case event
      Dado `Billing::OnEnrollmentApproved < Lucid::Case::Subscriber` com `subscribe Enrollment::Approve`
      Quando Enrollment::Approve tem sucesso e o evento é entregue
      Então Billing::OnEnrollmentApproved é chamado com o atributo event (Lucid::Case::Event)
      E event.content[:enrollment] é o record recarregado do banco
      E event.id é um UUID, event.name "enrollment.approve", event.type :ok, event.occurred_at preenchido

    Cenário: filtro on:
      Dado Subscribers com subscribe Payment::Charge (default), on: :failure, on: :any e on: :card_declined
      Quando Payment::Charge devolve failure(:card_declined)
      Então são chamados os de on: :failure, on: :any e on: :card_declined, e não o default

    Cenário: vários subscribe no mesmo Subscriber
      Dado um Subscriber com subscribe Enrollment::Approve, subscribe Enrollment::Reject, on: :any e subscribe :credit_limit_reached
      Quando os três eventos acontecem
      Então o Subscriber é chamado três vezes, distinguindo por event.name

    Cenário: Subscriber transacional sem eventos próprios
      Dado um Subscriber que chama Billing::StartInvoice.call(...) e devolve success
      Então ele roda em transação (o command interno vira savepoint)
      E o Subscriber não gera Case event; Billing::StartInvoice gera o seu

    Cenário: assinatura externa e bloco global
      Dado `Billing::OnEnrollmentApproved.subscribe(Enrollment::Approve)` dentro de config.to_prepare
      E `Lucid::Case.subscribe(Enrollment::Approve, as: :guardian_mailer) { |event| ... }`
      Quando Enrollment::Approve tem sucesso
      Então os dois são chamados, cada um na sua Delivery

    Cenário alternativo: subscribe fora de Subscriber
      Quando um Command ou uma Query declara subscribe
      Então o carregamento levanta Lucid::Case::Error::SubscribeOutsideSubscriber

    Cenário alternativo: assinatura inválida
      Quando um Subscriber assina uma Query, outro Subscriber, um step inexistente no alvo, on: em Custom event, ou on: com valor desconhecido
      Então a declaração levanta Lucid::Case::Error::InvalidSubscription

    Cenário: reload em desenvolvimento
      Dado um app com config.eager_load = false e Subscribers em app/models
      Quando o app sobe e quando o código é recarregado
      Então os Subscribers de config.events.load_paths estão carregados e registrados uma única vez (sem duplicar no reload)
      E um load_path inexistente levanta ArgumentError no boot

### Entrega

    Cenário: relay após commit com transport :active_job
      Dado store :outbox, transport :active_job e 2 assinantes de Enrollment::Approve
      Quando o case commita
      Então o relay roda in-process logo após o commit, enfileira 2 Lucid::Case::Events::DeliveryJob (um por Delivery) e marca delivered_at

    Cenário alternativo: Delivery que falha não afeta a outra
      Dado 2 assinantes, um deles levantando exceção
      Então só o job desse assinante é reexecutado (retry_on com config.events.delivery_attempts)
      E um assinante case que devolve failure é tratado como entregue (sem retry)

    Cenário alternativo: crash entre commit e relay
      Dado uma linha sem delivered_at e com created_at mais velho que 1 minuto
      Quando Lucid::Case::Events.relay_pending roda
      Então a linha é entregue e marcada
      E duas execuções concorrentes de relay_pending não entregam a mesma linha enquanto o claim (claimed_at) não expira

    Cenário alternativo: transport falha no relay in-process
      Dado um transport que levanta exceção no publish
      Quando o case commita
      Então a exceção não sobe para o chamador (o case já commitou), a linha fica pendente e relay_pending a entrega depois

    Cenário: purge pela retenção
      Dado config.events.retention = 7.days e purge :enabled
      Quando relay_pending roda
      Então linhas entregues há mais de 7 dias são apagadas e linhas não entregues nunca são apagadas
      E com purge :disabled nada é apagado

    Cenário: contexto restaurado na entrega
      Dado config.events.context = -> { { tenant: Current.tenant } } e config.events.around_delivery que restaura Current.tenant
      Quando o evento é gravado com Current.tenant "alfa" e entregue num job sem Current
      Então o assinante roda com Current.tenant "alfa" e event.context == { tenant: "alfa" }

    Cenário: transport do app
      Dado config.events.transport = um objeto com publish(event)
      Quando o case commita
      Então publish recebe o Lucid::Case::Event, e Lucid::Case::Event.from_h(event.to_h) reconstrói um evento igual

    Cenário: tabela com nome qualificado
      Dado config.events.table_name = "public.lucid_case_events" (Postgres) ou outro nome
      Então gravação, relay e purge usam essa tabela

    Cenário: store :inline
      Dado store :inline
      Quando o case commita
      Então os assinantes rodam in-process logo após o commit, sem tabela e sem job, com o payload passando pela mesma serialização
      E num rollback da transação externa nenhum assinante roda

### Deduplicação

    Cenário: Delivery repetida é ignorada
      Dado config.events.deduplication = :enabled
      Quando o mesmo DeliveryJob roda duas vezes para (evento, Billing::OnEnrollmentApproved)
      Então o Subscriber executa uma vez e existe 1 linha em lucid_case_deliveries
      E num Subscriber transacional a marcação entra na mesma transação: se ele falhar, a marcação é desfeita e o retry executa de novo

    Cenário alternativo: bloco sem nome com deduplicação
      Dado deduplication :enabled
      Quando Lucid::Case.subscribe(Enrollment::Approve) { } é declarado sem as:
      Então levanta Lucid::Case::Error::InvalidSubscription

    Cenário alternativo: deduplicação com :inline
      Quando configuro deduplication :enabled e store :inline
      Então Lucid::Case.configure levanta ArgumentError

### stale_on

    Cenário: invalidar tudo da query
      Dado Dashboard::Evolution (Query com cache) com stale_on Enrollment::Approve
      Quando Enrollment::Approve tem sucesso e commita
      Então logo após o commit, no mesmo processo, Dashboard::Evolution.stale é chamado e o próximo call é miss

    Cenário: invalidar entrada mapeada
      Dado stale_on Enrollment::Approve, period: ->(event) { event.content[:enrollment].period }
      Quando o evento acontece para o period 2026-11
      Então só a entrada period: 2026-11 é invalidada e a de outro period continua hit

    Cenário alternativo: rollback não invalida
      Quando Enrollment::Approve roda dentro de uma transação externa que faz rollback
      Então stale não é chamado

    Cenário alternativo: stale_on independe do outbox
      Dado config.events.recording = :disabled
      Então stale_on funciona igual (não grava nada no outbox)

    Cenário alternativo: stale_on fora de Query
      Quando um Command ou Subscriber declara stale_on
      Então levanta Lucid::Case::Error::InvalidSubscription

### Ordem

    Cenário: assinante ordenado
      Dado subscribe Ledger::Post, ordered: true num Subscriber e 3 eventos de Ledger::Post
      Quando o segundo falha na primeira tentativa
      Então o terceiro não é entregue antes do segundo, e após o retry os três foram entregues na ordem de gravação
      E duas execuções concorrentes do job ordenado não processam o mesmo assinante ao mesmo tempo

    Cenário alternativo: purge preserva pendentes ordenados
      Dado um evento entregue ao transport há mais de retention mas ainda não processado por um assinante ordenado
      Quando relay_pending faz purge
      Então esse evento não é apagado

### Testes

    Cenário: helpers Minitest
      Dado `include Lucid::Case::TestHelpers` (require "lucid/case/test_helpers")
      Então assert_event(Enrollment::Approve) { Enrollment::Approve.call(...) } passa
      E assert_event(Payment::Charge, type: :card_declined, content: { payment: payment }) compara tipo e conteúdo
      E assert_no_event(Enrollment::Approve) { ... } e capture_events { ... } (lista de Lucid::Case::Event) funcionam num teste transacional do Rails

    Cenário: matchers RSpec
      Dado require "lucid/case/rspec"
      Então expect { ... }.to emit_event(Enrollment::Approve).with(type: :ok, content: { enrollment: enrollment }) passa
      E expect { ... }.not_to emit_event(Enrollment::Approve) passa quando nada é emitido

    Cenário: generator de eventos
      Quando rodo bin/rails g lucid:case:events
      Então são criadas as migrations de lucid_case_events, lucid_case_deliveries e lucid_case_cursors
      E config/initializers/lucid_case_events.rb com recording :enabled, store :outbox fora de teste e :inline em teste, e as demais opções comentadas com default

## Nomes e objeto evento

- Case event e Step event: `name` = classe em snake_case com `::` → `.` (`Enrollment::Approve` → `enrollment.approve`); Step event tem o mesmo `name` e `step` preenchido.
- Custom event: `name` = `to_s` do symbol/string dado ao `emit` (`:credit_limit_reached` e `"credit_limit_reached"` são o mesmo evento). `kind` distingue `case`, `step` e `custom`, então um Custom event `"enrollment.approve"` não colide com o Case event.
- `Lucid::Case::Event` (congelado): `id` (UUID), `kind`, `name`, `source` (nome da classe que gerou), `step`, `type` (`:ok` ou o tipo da falha; `nil` em Custom), `success?`, `input`, `content`, `context`, `occurred_at`, `to_h`, `.from_h`.
- `input`: atributos do case (filtrados por `filter_parameters`); `{}` em Custom event e quando `event_payload` é declarado. `content`: conteúdo do Result (Case event), do `continue`/`skip_to`/`success` do step (Step event), os kwargs do `emit` (Custom event), ou o retorno de `event_payload`.

# why

O luneta publica `pedagogical.*` com `ActiveSupport::Notifications.instrument` à mão, alguns antes do commit, e assina tudo num `subscribers.rb` sem garantia de entrega: se o processo cair após o commit, o job pedagógico nunca roda; se a transação reverter depois do instrument, o job roda para dado inexistente. A spec de Evento de atividade do luneta teria que montar seu próprio encanamento (`ApplicationUseCase` com `after_success`/`after_commit`), e `lucid-hotel`/`lucid-tower` repetiriam isso. A gem já sabe o que é Command, transação e commit; é o lugar certo para garantir "o evento existe se e só se os dados existem", entregar cada reação isolada com retry, e ainda invalidar cache de query quando o dado que ela lê muda, coisa que hoje é `stale` manual espalhado.

# how

Regras de execução: TDD (o **tester** escreve o teste que falha a partir do Gherkin; o builder implementa), testes Minitest no padrão Arrange/Act/Assert dos testes existentes, sem comentários explicativos (YARD só na API pública). Cada PR roda `bundle exec rake test` verde. CI em ubuntu 3.2/3.4 e macOS 3.4 (`.github/workflows/ci.yml`), sqlite em memória: nada específico de Postgres no código (claim por `UPDATE ... WHERE`, sem `SKIP LOCKED`; `json` como tipo de coluna).

**Feature flag:** não há Flipper numa gem. A chave é `config.events.recording`, default `:disabled`: a mudança é aditiva e invisível até o app ligar (e rodar a migration). `stale_on` só age em queries que o declaram.

**Telas:** sem telas.

**Staging:** `staging: none` (gem; repo sem `AGENTS.md` com seção Staging).

**Integração:** `integration: pr` (default global), PRs empilhados abaixo.

## Desenho

**Configuração** (`config.events`, objeto `Lucid::Case::Events::Configuration`, `Lucid::Case.configure` valida):

| opção | default | |
|---|---|---|
| `recording` | `:disabled` | `:enabled`/`:disabled`; command sobrescreve com `events :enabled\|:disabled` |
| `store` | `:outbox` | `:outbox` ou `:inline` |
| `transport` | `:active_job` | ou objeto que responde a `publish(event)` |
| `queue` | `:default` | fila dos jobs da gem |
| `delivery_attempts` | `5` | `retry_on StandardError` do `DeliveryJob` |
| `table_name` | `"lucid_case_events"` | aceita nome qualificado |
| `deliveries_table_name` | `"lucid_case_deliveries"` | |
| `cursors_table_name` | `"lucid_case_cursors"` | |
| `retention` | `7.days` | |
| `purge` | `:enabled` | purge dentro de `relay_pending` |
| `claim_timeout` | `5.minutes` | claim expirado volta a ser relayável |
| `deduplication` | `:disabled` | exige `store :outbox` (`ArgumentError`) |
| `load_paths` | `%w[app/models]` | relativo a `Rails.root`; inexistente → `ArgumentError` no boot |
| `context` | `nil` | callable chamado na gravação; resultado (Hash serializável) vai para a linha |
| `around_delivery` | `nil` | `->(context, &block)` envolve cada Delivery |

**Tabelas** (migrations do generator, `t.json` funciona em sqlite e Postgres):
- `lucid_case_events`: `uuid` (string, único), `kind`, `name`, `source`, `step` (null), `result_type` (null), `payload` (json: `input`/`content` serializados), `context` (json), `occurred_at`, `claimed_at` (null), `delivered_at` (null), `created_at`. Índices: `uuid` único, `(delivered_at, id)`, `(name, kind)`.
- `lucid_case_deliveries`: `event_uuid`, `subscriber` (string), `created_at`; único `(event_uuid, subscriber)`.
- `lucid_case_cursors`: `subscriber` (único), `last_event_id` (bigint).

**Gravação** (`Lucid::Case::Events`, módulo incluído em `Lucid::Case`, só age em Command com recording efetivo `:enabled`):
- Sucesso: o Case event é gravado dentro de `lucid_isolated` logo após os hooks `after_success`, antes do commit.
- Falha: gravado depois que `lucid_with_transaction` devolve (savepoint já revertido), portanto dentro da transação externa se houver.
- Exceção que sobe: nada. `catch` que devolve failure: conta como falha.
- `emit`: grava na hora no store (`:outbox`) ou enfileira no buffer da instância (`:inline`), dentro da transação corrente; Query/Subscriber → `EmitOutsideCommand`.
- Step event: gravado ao fim de um step que devolve `continue`/`skip_to`/`success`, **somente** se o registry tem assinatura `(classe, step)`.
- Serialização: `ActiveJob::Arguments.serialize` de `{input:, content:}`, com `input` passando antes por `configuration.parameter_filter`; `ActiveJob::SerializationError` vira `Error::UnserializableEvent` (levantado dentro da transação, então faz rollback).
- Após a transação mais externa commitar (`ActiveRecord.after_all_transactions_commit`): `:outbox` → relay in-process dos uuids gravados por este case (erros do transport são engolidos e logados via `config.logger`, a linha fica pendente); `:inline` → entrega síncrona de cada Delivery.

**Registry e assinatura** (`Lucid::Case::Events::Registry`, thread-safe, `clear!`):
- `subscribe(target, on: :success, step: nil, ordered: false)` no `Lucid::Case::Subscriber`; em Command/Query → `SubscribeOutsideSubscriber`. `target` é classe Command (Case/Step event) ou Symbol/String (Custom event).
- `on:` aceita `:success`, `:failure`, `:any`, um Symbol de tipo de falha ou Array deles; em Custom event → `InvalidSubscription`.
- `Lucid::Case.subscribe(target, as: nil, **opts, &block)`: bloco global; `as:` (Symbol/String) obrigatório quando `deduplication` ou `ordered:`.
- Identidade da Delivery: nome da classe do Subscriber ou `as:`.
- Railtie: `config.to_prepare` do gem (registrado antes dos initializers do app) faz `Registry.clear!` e, com `eager_load` false, `Rails.autoloaders.main.eager_load_dir` para cada `load_paths`.

**Subscriber** (`Lucid::Case::Subscriber`, `kind :subscriber`): atributo `event` declarado pelo kind, transacional como Command (`transaction :disabled` permitido, hooks permitidos), sem Case event nem `emit`, aceita `step`/`catch`/`finally`. `KINDS` passa a `%i[command query subscriber]` e `transactional?` vale para command e subscriber.

**Entrega** (`:outbox`):
- `Relay#relay(ids)`: claim por `UPDATE ... SET claimed_at = now WHERE id IN (...) AND delivered_at IS NULL AND (claimed_at IS NULL OR claimed_at < now - claim_timeout)`; para cada linha reivindicada chama `transport.publish(event)` e marca `delivered_at`.
- Transport `:active_job`: para cada assinatura que casa (`name`, `kind`, `step`, `on:`), enfileira `DeliveryJob.perform_later(event_uuid, subscriber_id)` (não ordenadas) ou `OrderedDeliveryJob.perform_later(subscriber_id)` (ordenadas, PR 8).
- `DeliveryJob`: carrega a linha (sumiu por purge → descarta e loga), monta o `Event` (desserializa), chama `around_delivery(context) { invoke }`; `invoke` = `Subscriber.call(event:)` ou `block.call(event)`; Result failure = entregue; exceção = retry.
- `Lucid::Case::Events.relay_pending`: relay das linhas pendentes com `created_at < 1.minute.ago` em lotes de 500; depois, com `purge :enabled`, apaga entregues com `delivered_at < retention.ago` (preservando pendentes de cursores ordenados, PR 8). O app agenda (cron, solid_queue recurring); o guia mostra os dois.

**Deduplicação**: em `DeliveryJob`, com `deduplication :enabled`, insere `(event_uuid, subscriber)` em `lucid_case_deliveries`: num Subscriber transacional, dentro da transação dele (antes do corpo); num bloco ou Subscriber `transaction :disabled`, antes de invocar. `ActiveRecord::RecordNotUnique` → Delivery já feita, ignora.

**stale_on** (`Lucid::Case::Cache`, só Query): `stale_on target, on: :success, step: nil, **mapping` (cada valor é `->(event)`). Registra no registry como assinatura in-process. Disparo: no mesmo ponto pós-commit do case publicador, no mesmo processo, sem serialização, independente de `recording` e do store. Sem mapping → `Query.stale`; com mapping → `Query.stale(**mapping.transform_values { _1.call(event) })`.
