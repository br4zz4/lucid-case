# Gem lucid-case — use cases Command/Query com transação, hooks, steps e cache

> **TLDR**: extrair o antigo `lib/lucid` do luneta (removido em `4f902eb`) para a gem genérica `lucid-case` (`br4zz4/lucid-case`, módulo `Lucid::Case`), reescrita para ser thread-safe, com Command (transacional por padrão) e Query (somente leitura, cacheável), steps, `catch`, hooks e documentação completa; depois migrar os 59 use cases do luneta de `Micro::Case` para ela e remover o u-case.

Spec 1 de 3 da família `Lucid` (`lucid-case` → `lucid-hotel` → `lucid-tower`). Decisão: `docs/adr/0005-replace-u-case-with-lucid-case.md`.

# what

Como dev Brazza, quero uma gem própria de use cases, genérica para qualquer app Rails, que separe command de query, garanta transação e efeitos depois do commit, e cacheie queries pelos argumentos de entrada, para parar de reescrever esse encanamento em cada case e ter um padrão reutilizável entre projetos.

## out of scope

- Adotar a gem no has_warranty (segue em u-case 5.7).
- Circuit breaker (ideia futura da gem, registrada no `docs/roadmap.md` dela).
- Camada de compatibilidade com `Micro::Case` (`Success(result:)`, `Micro::Cases.flow`).
- Eventos de atividade (`ApplicationUseCase`, `ActivityEvent`): a spec `20261118150000_activity_events.md` passa a se apoiar nos hooks desta gem num ajuste posterior; aqui nenhum hook de evento é usado.
- Publicar no RubyGems (consumo via `github:` + `tag:`).
- Cachear qualquer query do luneta além de `Dashboard::CumulativeEvolution`.
- Reescrever o dashboard de acquisition em Stimulus Reflex; o refresh é um POST comum.

## acceptance criteria

### Gem

    Cenário: command com sucesso
      Dado `class Users::Create < Lucid::Case::Command` com `attributes :params` e `def call! = success(user: User.create!(params))`
      Quando chamo `Users::Create.call(params: { name: "Ana" })`
      Então o resultado tem `success?` true, `type` :ok e `result[:user]` com o usuário salvo

    Cenário: falha tipada
      Dado um case cujo `call!` devolve `failure(:not_found, id: 1)`
      Quando ele é chamado
      Então `failure?` é true, `type` é :not_found, `result[:id]` é 1 e `on_failure(:not_found) { }` executa o bloco
      E `on_failure(:other) { }` e `on_success { }` não executam

    Cenário: falha sem tipo
      Quando o case devolve `failure(reason: "x")`
      Então `type` é :error

    Cenário alternativo: validação de entrada
      Dado `validates :params, presence: true, kind: Hash`
      Quando chamo com `params: nil` ou `params: "x"`
      Então o resultado é `failure` com `type` :invalid_attributes e `result[:errors]` é um `ActiveModel::Errors`
      E o `call!` não é executado

    Cenário alternativo: retorno que não é Result
      Quando o `call!` devolve `nil` ou um Hash
      Então `.call` levanta `Lucid::Case::Error::UnexpectedResult`

    Cenário: isolamento entre instâncias concorrentes
      Dado 50 threads chamando o mesmo case com valores de `attributes` diferentes
      Quando todas terminam
      Então cada resultado contém exatamente o valor da própria chamada

    Cenário: isolamento por herança
      Dado `Base < Lucid::Case::Command` com `attributes :a` e `Child < Base` com `attributes :b` e um `step`
      Então `Base` só conhece `:a` e não tem steps, e `Child` conhece `:a` e `:b`

    Cenário alternativo: call! e steps no mesmo case
      Quando uma classe define `call!` e declara `step`
      Então o carregamento da classe levanta `Lucid::Case::Error::AmbiguousDefinition`

    Cenário: command transacional faz rollback na falha
      Dado um Command (default `transaction :enabled`) que cria um registro e devolve `failure(:x)`
      Quando é chamado
      Então o registro não existe no banco e o resultado é a falha

    Cenário: command transacional faz rollback na exceção
      Quando o `call!` cria um registro e levanta `RuntimeError` sem `catch`
      Então o registro não existe e a exceção sobe para quem chamou

    Cenário: transação desligada no case
      Dado `transaction :disabled` e um `call!` que grava status "failed" e devolve `failure(:x)`
      Então o status "failed" permanece gravado

    Cenário: transação desligada globalmente
      Dado `Lucid::Case.configure { |c| c.transaction = :disabled }` e um Command sem declaração
      Então ele roda sem transação, e um Command com `transaction :enabled` roda com transação

    Cenário: case aninhado usa savepoint
      Dado um Command externo que grava A, chama um Command interno que grava B e falha, e o externo devolve sucesso
      Então A está gravado e B não

    Cenário: ordem dos hooks
      Dado `after_success`, `after_failure` e `after_commit` declarados
      Quando o case tem sucesso dentro de uma transação externa do chamador
      Então `after_success` roda dentro da transação, antes do commit
      E `after_commit` roda só depois do commit da transação mais externa
      E se a transação externa fizer rollback, `after_commit` não roda
      E na falha só `after_failure` roda

    Cenário: instrumentação
      Quando qualquer case é chamado
      Então é publicado `call.lucid_case` com `case`, `kind`, `type`, `cache` (:hit, :miss, :bypass ou nil) e duração

    Cenário: query não grava
      Dado `class Report < Lucid::Case::Query` cujo `call!` faz `User.create!`
      Quando é chamada
      Então levanta `ActiveRecord::ReadOnlyError` e nada é gravado

    Cenário alternativo: declarações proibidas
      Quando uma Query declara `transaction`, `after_success`, `after_failure` ou `after_commit`
      Então o carregamento levanta `Lucid::Case::Error::SideEffectInQuery`
      E quando um Command declara `cache` o carregamento levanta `Lucid::Case::Error::CacheOnCommand`
      E quando uma classe redeclara `kind` com outro valor ou um valor desconhecido o carregamento levanta `Lucid::Case::Error::InvalidKind`

    Cenário: kind declarado direto no Lucid::Case
      Dado `class R < Lucid::Case` com `kind :query`
      Então `R.query?` é true e o comportamento é idêntico a herdar de `Lucid::Case::Query`

    Cenário: steps
      Dado um case com `step(:a) { continue(x: 1) }`, `step(:b) { skip_to(:d) }`, `step(:c) { ... }` e `step(:d) { success(y: 2) }`
      Quando é chamado
      Então `:c` não executa e o resultado é sucesso com `x: 1` e `y: 2`

    Cenário: acúmulo de conteúdo configurável
      Dado `step(:a) { continue(x: 1) }`, `step(:b) { continue(y: 2) }` e `step(:c) { success(z: 3) }`
      Então por padrão (`config.accumulate = :enabled`) o resultado tem `x: 1, y: 2, z: 3`
      E com `accumulate :disabled` no case, ou `config.accumulate = :disabled`, o resultado tem só `z: 3`
      E `accumulate :enabled` no case sobrescreve o global e subclasses herdam o valor do pai

    Cenário: logging configurável
      Dado `config.logging = :disabled` (default)
      Então nenhum case loga
      E com `config.logging = :enabled`, ou `logging :enabled` no case, cada chamada loga `called input=[chaves]`, cada step (`step :x -> continue|skip_to|success|failure`), exceções do step e do `catch` (warn) e o resultado com duração e `cache=hit|miss|bypass`
      E `logging :disabled` no case silencia mesmo com o global ligado, e subclasses herdam
      E por padrão só nomes (chaves de entrada e de conteúdo) vão para o log; com `config.log_values = true`, ou `logging :enabled, values: true` no case, os valores saem filtrados por `filter_parameters` (`[FILTERED]`)
      E dentro do case, `logger.debug|info|warn|error(msg)` (ou com bloco) escreve `[Lucid::Case] <Classe> <msg>` respeitando o `logging` do case
      E `config.log_level` (`:debug|:info|:warn|:error`) e `config.logger` são respeitados, e sem logger nada quebra

    Cenário: finally sempre roda
      Dado `finally(:release_lock) { lock.release }` num case, com `call!` ou com steps
      Então roda depois do sucesso, da failure e da exceção (capturada ou não), em ordem de declaração
      E roda depois do `catch` e com a transação já fechada, sem alterar o resultado
      E não roda quando o resultado vem do cache, e uma exceção dentro do `finally` propaga

    Cenário: catch devolve o próprio Result
      Dado `catch(Timeout::Error) { |ctx| failure(:timeout, error: ctx.error.message) }`
      Quando um step levanta `Timeout::Error`
      Então o resultado é `failure` com `type` :timeout

    Cenário: catch sem Result explícito
      Quando o handler do `catch` não devolve Result
      Então o resultado é `failure(:exception, error: <a exceção>)`

    Cenário alternativo: exceção sem catch correspondente
      Quando um step levanta um erro de classe não declarada em nenhum `catch`
      Então a exceção sobe

    Cenário: catch com classe namespaced e handlers repetidos
      Dado `catch(Foo::Bar::Error)` declarado duas vezes
      Então os dois handlers rodam em ordem de declaração e o último Result devolvido vale

    Cenário: cache hit
      Dado `class Stats < Lucid::Case::Query` com `cache duration: 5.minutes` e store em memória
      Quando chamo `Stats.call(period:)` duas vezes com o mesmo `period`
      Então o `call!` executa uma vez, o segundo resultado tem `cached?` true e o mesmo `content`
      E `cached_at` e `expires_at` estão preenchidos

    Cenário: entradas diferentes não se misturam
      Quando chamo com `period` 1 e com `period` 2
      Então o `call!` executa duas vezes

    Cenário: registro alterado invalida a entrada
      Quando o `period` é atualizado (muda `cache_key_with_version`) e chamo de novo
      Então o `call!` executa de novo

    Cenário: escopo isola tenants
      Dado `cache_scope = -> { Thread.current[:tenant] }`
      Quando chamo com o mesmo `period` id sob os escopos "alfa" e "beta"
      Então o `call!` executa uma vez por escopo

    Cenário: fresh, stale e version
      Então `Stats.fresh.call(period:)` executa e regrava mesmo com entrada válida
      E `Stats.stale(period:)` invalida só aquela entrada e devolve true
      E `Stats.stale` e `Stats.stale(:period)` (ou vários nomes, `stale(:period, :grade)`) fazem todas as entradas do escopo atual executarem de novo, sem afetar outros escopos
      E `Stats.stale(:inexistente)` e `Stats.stale(:period, grade: 1)` levantam `ArgumentError`
      E trocar `cache version: 2` faz todas as entradas executarem de novo

    Cenário alternativo: falha não vai para o cache
      Quando a query devolve `failure`
      Então a próxima chamada executa o `call!` de novo

    Cenário alternativo: entrada não cacheável
      Quando chamo uma query cacheada passando um Proc
      Então levanta `Lucid::Case::Error::UncacheableInput`

    Cenário alternativo: cache desligado
      Dado `cache :disabled` no case, ou `perform_caching = false` global
      Então o `call!` executa em toda chamada e `cached?` é false

    Cenário alternativo: fail fast de configuração
      Dado `perform_caching = true`
      Quando o store efetivo é `nil` ou `ActiveSupport::Cache::NullStore`
      Então o boot levanta `Lucid::Case::Error::CacheStoreMissing`
      E quando `cache_scope` não foi definido o boot levanta `Lucid::Case::Error::MissingCacheScope`
      E `cache_scope = :global` é aceito

    Cenário: plataforma
      Quando o CI da gem roda
      Então a suíte passa em ubuntu Ruby 3.2, ubuntu Ruby 3.4 e macOS Ruby 3.4

# why

O luneta tem 59 use cases sobre u-case 4.5 com o mesmo encanamento repetido à mão: `ActiveRecord::Base.transaction do` em cerca de 10 cases, `rescue` virando `Failure`, jobs enfileirados dentro da transação (`organization/create.rb:16`: se houver rollback, o job roda para uma escola inexistente) e notificações publicadas antes do commit. Nada distingue um case que grava de um que só calcula, então nada impede uma "query" de gravar nem permite cachear com segurança. O `lib/lucid` que já existiu resolvia parte disso com uma DSL própria, mas tinha bugs graves (valor de atributo vazando entre instâncias concorrentes via `define_method` na classe, `@@class_variables` vazando entre subclasses, `map!` corrompendo validações) e saiu do repo sem destino. Uma gem genérica na br4zz4 corrige isso uma vez, dá à família `Lucid` (próximas: `lucid-hotel`, `lucid-tower`) a base de use cases, e prepara os hooks que a spec de eventos de atividade precisa.

# how

Regras: TDD (o tester escreve o teste que falha a partir do Gherkin; o builder implementa). Na gem, Minitest em `test/**`; no luneta, RSpec Triple-A sem `let`. Sem comentários explicativos no código; a API pública da gem leva documentação YARD (contrato público). Cada PR do luneta termina com `make core.check`; cada PR da gem com `bundle exec rake test`.

**Feature flag:** não. Na gem, tudo é novo. No luneta, a troca de base de cada case mantém o comportamento observável (mesmos tipos de falha e chaves de resultado), e o único comportamento novo (cache do gráfico + botão) é aditivo e só liga com Redis configurado.

**Telas criadas/editadas:** `/acquisition` (card "Evolução de Contratos"). Rota nova sem tela: `POST /acquisition/evolution_refresh`. Removida: nenhuma rota (o `DashboardController` raiz não tinha rota).

**Staging:** `staging: none`.

## Desenho da gem

Repo `~/workspace/br4zz4/lucid-case` → `github.com/br4zz4/lucid-case`. Gem `lucid-case`, `require "lucid/case"`, módulo `Lucid::Case`. Nada é definido solto em `Lucid` (o módulo é compartilhado pela família). Ruby `>= 3.2`; dependências `activemodel`, `activesupport`, `activerecord` `>= 7.2, < 9` (precisa de `ActiveRecord.after_all_transactions_commit`). MIT. Fonte: `git show 4f902eb^:lib/lucid/{case,attributable,callable,step_case,contractable}.rb` do luneta; a DSL é mantida, os internals são reescritos com referência em u-case, dry-transaction, ActiveInteraction e Interactor.

**Estado de classe:** attributes, kind, transaction, cache, steps, catches e hooks ficam em atributos de classe copiados no `inherited` (`dup`), nunca em `@@vars`. Valores de entrada ficam em variáveis de instância; leitores são definidos uma vez na declaração `attributes`, nunca no `initialize`.

**Arquivos:**
- `lib/lucid-case.rb` (requer `lucid/case`)
- `lib/lucid/case.rb` (classe base, inclui os módulos abaixo)
- `lib/lucid/case/version.rb` (`Lucid::Case::VERSION = "0.1.0"`)
- `lib/lucid/case/errors.rb` (`Lucid::Case::Error` e subclasses `UnexpectedResult`, `AmbiguousDefinition`, `InvalidKind`, `SideEffectInQuery`, `CacheOnCommand`, `UncacheableInput`, `CacheStoreMissing`, `MissingCacheScope`)
- `lib/lucid/case/result.rb`
- `lib/lucid/case/attributes.rb`
- `lib/lucid/case/validations.rb` e `lib/lucid/case/kind_validator.rb`
- `lib/lucid/case/configuration.rb`
- `lib/lucid/case/kinds.rb`, `lib/lucid/case/command.rb`, `lib/lucid/case/query.rb`
- `lib/lucid/case/transaction.rb`, `lib/lucid/case/hooks.rb`, `lib/lucid/case/instrumentation.rb`
- `lib/lucid/case/stepped.rb`, `lib/lucid/case/catching.rb`
- `lib/lucid/case/cache.rb`, `lib/lucid/case/cache/key.rb`, `lib/lucid/case/cache/store.rb`, `lib/lucid/case/cache/invocation.rb`
- `lib/lucid/case/railtie.rb`
- `lib/generators/lucid/case/install/install_generator.rb` e `templates/lucid_case.rb.tt`

**API de definição:**
- `attributes :a, :b` e `attribute :x, default: valor` (também `attributes :a, :b, default: nil`); chaves desconhecidas são ignoradas.
- `validates` do ActiveModel. Falha de validação → `failure(:invalid_attributes, errors: <ActiveModel::Errors>)` sem executar o corpo. A gem traz `KindValidator` (`validates :params, kind: Hash`, aceita classe ou array de classes), compatível com o uso atual do luneta.
- `kind :command | :query` (default `:command`). `Lucid::Case::Command` e `Lucid::Case::Query` são subclasses que só declaram o kind. Redeclarar o mesmo valor é aceito; outro valor ou valor desconhecido → `InvalidKind`. Predicados `kind`, `command?`, `query?`.
- Corpo: `def call!` **ou** `step(:nome) { ... }`; os dois → `AmbiguousDefinition` no momento da segunda declaração (vale para `step` após `call!` e para `method_added(:call!)` após `step`).
- Dentro do corpo: `success(**content)`, `failure(type = :error, **content)`. Em steps: `continue(**content)` acumula conteúdo e segue; `skip_to(:step, **content)` pula até o step; `success`/`failure` encerram. O Result final recebe o conteúdo acumulado (o conteúdo explícito vence em conflito).
- `catch(ErrorClass, ...) { |ctx| }` (vale para `call!` e steps): `ctx.error`, `ctx.case`. Handlers guardados como procs em ordem; todos os que casam rodam; o último Result devolvido vale; nenhum Result → `failure(:exception, error:)`. Sem handler que case → a exceção sobe.
- Command: `transaction :enabled | :disabled` (default vem de `config.transaction`, que é `:enabled`). Habilitada: `ActiveRecord::Base.transaction(requires_new: true)`; `failure` faz `raise ActiveRecord::Rollback` internamente e devolve o Result; exceção faz rollback e sobe (ou vira Result via `catch`, já fora da transação desfeita).
- Hooks (só Command), executados com `instance_exec(result)`: `after_success`, `after_failure` (dentro da transação quando habilitada; logo após o corpo quando não), `after_commit` (só no sucesso, via `ActiveRecord.after_all_transactions_commit`, que roda na hora se não houver transação aberta e é descartado se a mais externa fizer rollback).
- Query: o corpo roda em `ActiveRecord::Base.while_preventing_writes`. `transaction`/hooks → `SideEffectInQuery`. `cache :enabled | :disabled`, `cache duration: 5.minutes`, `cache :enabled, duration: 10.minutes`, `cache version: 2`. Em Command, `cache` → `CacheOnCommand`.

**Result** (`Lucid::Case::Result`, congelado): `success?`, `failure?`, `type`, `content` (= `data` = `to_h`), `[]`, `on_success { |r| }`, `on_failure(type = nil) { |r| }` (ambos devolvem `self`), `deconstruct_keys`, `cached?`, `cached_at`, `expires_at`, `case_class`. Um `call!` que não devolve Result → `UnexpectedResult`.

**Cache (só Query):**
- Liga quando `config.perform_caching` é true **e** o case está `:enabled` (declarado ou pelo default `config.cache`, que é `:disabled`).
- Chave: `lucid_case/<NomeDaClasse>/v<version>/<scope>/g<geração>/<SHA256 das entradas normalizadas>`. Normalização: `cache_key_with_version` para objetos que respondem a ele; Hash com chaves ordenadas, recursivo; Array recursivo; String, Symbol, Numeric, true/false/nil, Date, Time (ISO 8601). Qualquer outro tipo → `UncacheableInput`.
- Geração: contador por classe e escopo guardado no próprio store (`lucid_case/<Classe>/<scope>/generation`); `stale` incrementa.
- Só `success` é gravado; o Result gravado leva `cached_at`/`expires_at`; no hit, nada do case executa.
- `Classe.fresh` devolve um `Cache::Invocation` com `call(**in)` que executa, regrava e devolve. `Classe.stale(**in)` invalida a entrada (true/false); `Classe.stale` sem entradas, ou `Classe.stale(:atributo, ...)` com nomes de atributos (validados, `ArgumentError` se desconhecido ou misturado com entradas), invalida tudo do escopo atual.

**Configuração** (`Lucid::Case.configure { |c| }`): `transaction` (`:enabled`), `cache` (`:disabled`), `cache_duration` (`5.minutes`), `cache_store` (default: `Rails.cache`), `cache_scope` (lambda ou `:global`, sem default), `perform_caching` (default: `Rails.application.config.action_controller.perform_caching` quando o Rails existe; `true` fora dele). Validação no `after_initialize` do Railtie: `perform_caching` true + store `nil`/`NullStore` → `CacheStoreMissing`; `perform_caching` true + `cache_scope` indefinido → `MissingCacheScope`.

**Instrumentação:** `ActiveSupport::Notifications.instrument("call.lucid_case", case:, kind:, type:, cache:)`.

**Gerador:** `bin/rails g lucid:case:install` cria `config/initializers/lucid_case.rb` com todas as opções e defaults.

## Parte B — luneta (depois da tag `v0.1.0`)

Desvios registrados durante a implementação: a gem ganhou `accumulate` (conteúdo dos steps configurável) e `stale` (por entradas, por nomes de atributo ou tudo); a documentação separa `cache.md` e `catch.md`. `SubdomainProvisioning::Run` itera `STEPS` num único step `run_steps` (em vez de um step por etapa) para manter o contrato de `STEPS`. Os `rescue` simples dentro de `call!` ficaram como estão (a falha já faz rollback); só os de Contract::Create/Update, Organization::Create e SubdomainProvisioning::Run viraram `catch`.

Regras de migração aplicadas a cada case: `< Micro::Case` → `< Lucid::Case::Command` (grava) ou `< Lucid::Case::Query` (só calcula); `Success(result: { ... })` → `success(...)`; `Failure(:t, result: { ... })` → `failure(:t, ...)`; `Failure(result: { ... })` → `failure(...)`; `transaction do` manual sai (o default cobre); `rescue X => e` que vira `Failure` → `catch(X) { |ctx| failure(...) }`; `perform_later` e `ActiveSupport::Notifications.instrument` → `after_commit`. Controllers não mudam (`on_success`, `on_failure(:t)`, `[]`, `type` e `data` mantêm a semântica). Specs do case trocam `Micro::Case::Result` por `Lucid::Case::Result` onde aparecer. Se uma Query levantar `ActiveRecord::ReadOnlyError` no teste, o case vira Command e o PR registra.
